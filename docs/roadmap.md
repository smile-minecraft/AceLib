## 怎麼更新這份文件

這份文件是任務清單。`[ ]` 是還沒完成，`[x]` 是完成。

完成一個項目時，只把那一行的 `[ ]` 改成 `[x]`，其他都不動：

- 項目的文字不改寫，也不在後面加註結果、驗證方式、日期或測試數量。
- 段落標題不改名，項目不在段落之間搬動。
- 修了什麼、行為變成怎樣，寫進 [CHANGELOG.md](../CHANGELOG.md) 和對應的模組頁。
- 實機確認有自己的清單。程式修好但還沒上實機時，勾修正項目，不勾實機確認。

修正項目可以勾選的條件是：程式已修正，有先失敗、後通過的回歸測試，全部既有測試通過。

新增、刪除、改寫項目，或調整順序，屬於範圍變更，要先經維護者同意。提案時說明：

- 哪個下游 plugin 已經自己維護這段邏輯，位置在哪裡。沒有的話也請寫明。
- AceLib 負責的範圍，和留給下游判斷的部分。
- 驗收情境，包含 Paper 和 Folia 的差異。

版本發布後，整個版本的段落從這裡移除，內容以 CHANGELOG 為準。

## 規劃原則

AceLib 要讓下游 plugin 少寫重複的程式碼，也更容易寫對。規劃時依下列幾點判斷：

- 下游佐證決定先後。下游已經自己維護同類邏輯的項目先做，兩個下游都重複實作的排最前面。目前對照的下游是 ChunkLand 與 Ace-Economy。還沒有下游在用的項目排在後段，各項說明會寫明。
- AceLib 管流程和安全邊界。誰可以做什麼、價格、權限、操作對象，留給下游 plugin 判斷。
- 缺陷先修。新功能依賴的部分有已知缺陷時，先修缺陷。
- 公開 API 可以在版本之間變更。破壞性變更要先記在這份路線圖並標明版本，發布時寫進 CHANGELOG；公開型別有增減或簽章改變時，更新 [API surface](reference/api-surface.md) 分類和簽章基線。
- Paper 和 Folia 都要驗證。行為不同的功能要有兩組測試。牽涉時序和執行緒的項目還要實機驗證，MockBukkit 測不出真實 Folia 的行為。
- 每個新模組要有模組頁，consumer 範例裡要有能編譯的用法。

## AceLib 1.3.1 修補已知缺陷

這一版不加功能。AceLib 1.4.0 的任務作用域要靠 Folia 任務取消，介面流程要靠 reload 之後正常的 GUI 行為，這些缺陷得先修完。

### 修正項目

每一項先寫缺陷，再寫修正方向。

#### 排程

- [x] Folia 上的任務無法取消，實體退休時沒有通知。保存平台回傳的任務 handle 並轉發取消；實體在執行前被移除時解除追蹤。
- [x] 一次性任務完成後仍留在追蹤集合。任務執行結束、被取消，或平台回報實體已失效時，立即解除追蹤。
- [x] 以位置排程時，檢查 chunk 是否載入的方式本身會載入 chunk。只讀取既有的載入狀態，未載入時記 `ACELIB-SCHED-004`。
- [x] 實體在派送前已經失效時，被誤判成平台不支援。改記 `ACELIB-SCHED-003`，回傳安全的 no-op。
- [x] plugin 停用和派送同時發生時，底層留下任務。晚回來的 handle 仍要取消。

#### 資料

- [x] 巢狀路徑的 `remove` 回報成功，資料卻還在。走訪結果指向直接父層。
- [x] 資料含 null 值時 `snapshot()` 失敗，存檔跟著失敗。改用允許 null 的不可變檢視。
- [x] JSON store 關閉時寫入失敗沒有紀錄。失敗時記錄錯誤碼。
- [x] 遷移後被刪除的 key 仍殘留。遷移結果完整取代舊內容。
- [x] 寫入失敗留下暫存檔。清掉暫存檔；清理本身失敗也要留下紀錄，不覆蓋原始失敗原因。
- [x] migration 改到巢狀節點時，可能連帶改到呼叫端持有的讀取視圖。在 migration 內部隔離寫入範圍；`Record.copy()` 的淺拷貝語意是公開約定，不改。
- [x] `MemoryRecord.getRecord` 對 null 或空白 path 沒有驗證。和其他 path 方法一致，回報 `ACELIB-DATA-003`。
- [x] JDBC store 的主鍵長度在 MySQL 與 MariaDB 常見字元集下建不起來。主鍵改用 key 的雜湊，舊表在初始化時升級。
- [x] JSON store 取代檔案前沒有強制落盤。暫存檔寫完先落盤，再取代。

#### 事件

- [x] 註冊父類事件時收不到子類事件。依型別相容性分發。
- [x] 同一事件型別反覆註冊、解除之後，listener 被重複觸發。每個事件型別只向平台註冊一次。

#### 冷卻

- [x] 並行呼叫時可能同時通過冷卻。改成原子操作。
- [x] 過期的冷卻紀錄不會清除。清理過期紀錄。

#### 設定與語系

- [x] reload 失敗沒有紀錄。失敗時記錄原因。
- [x] 設定檔寫入不是原子操作。先寫暫存檔再取代；寫入或搬移失敗時清掉暫存檔，保留原始錯誤。
- [x] 設定檔版本比程式新時，會被改寫成舊版本號。拒絕降級並回報；載入與重載共用同一條版本路徑。
- [x] 缺訊息 key 時每次都輸出警告。同一個缺失只警告一次。
- [x] 找不到的語系檔每次查詢都讀磁碟。記住不存在的語系檔；損壞與不存在以不同代碼區分。

#### 世界

- [x] 鄰近實體查詢會掃過整個世界的實體。改用以範圍查詢的平台 API。
- [x] 播放效果沒有實作卻回報成功。實作效果，或明確回報不支援。

#### 生命週期與上下文

- [x] AceLib 自己的 reload 沒有關閉舊的 GUI 與世界服務，舊的 GUI listener 會取消新 GUI 的點擊。reload 時先解除舊服務和 listener，再建立新的。
- [x] `SafeExecutor` 每次呼叫都建立新的排程器，錯誤進不了診斷，停用後還能排程。共用 plugin 的排程器。

#### 玩家資料

- [x] reload 之後線上玩家失去 session，離線時資料不會保存。重新建立服務後，為線上玩家補建 session。
- [x] 載入和保存失敗沒有任何紀錄。在 listener 處理失敗結果，記錄錯誤碼。
- [x] 快速重連，或離線時保存失敗之後，該玩家無法再建立 session。等舊 session 結束或允許取代；失敗的 session 要能重試或釋放。
- [x] 停用時為每位玩家各保存一次整個檔案，等待時間又很短。全部資料寫回後只保存一次，等待時間依資料量調整。

#### GUI

- [x] 確認操作的回呼在鎖內執行。狀態轉換完成、離開鎖之後再執行回呼。

### 實機確認

#### Folia

- [x] 取消後的重複任務不再執行。
- [x] 延遲為 0 的任務會執行。
- [x] reload 之後，線上玩家離線和重登都沒有玩家資料錯誤。
- [x] 未載入 chunk 的位置排程被拒絕並記 `ACELIB-SCHED-004`，事後 chunk 仍未載入。

## AceLib 1.4.0 新功能

原本分散在後續版本的規劃都併進這一版，共十一項，依相依關係分成四個階段。階段是動工順序。

前兩個階段的項目，下游都已經有自己維護的程式碼。第三、第四階段有幾項目前沒有下游在用，是維護者決定排入的，各項會寫明。

每一項底下的清單是交付內容，做完一條勾一條。

### 第一階段 測試與排程

#### 測試套件

ChunkLand 和 Ace-Economy 各寫了一份 GUI 假實作，另外還有排程、表單、基岩服務的 stub。兩邊的程式碼重複，也容易和 AceLib 的實際行為對不上。

測試套件提供這些假實作，給下游寫單元測試用。真實伺服器上的驗收由 Docker 管理的測試環境負責，不在測試套件的範圍。

- [x] 確認 Gradle 的 test fixtures 產出的 jar 可以透過 JitPack 發布，下游能在測試時引用。行不通就回到[待決事項](#待決事項)重新決定發布方式。
- [ ] 測試 jar 也附在 GitHub Release 上，發布 workflow 跟著調整。ChunkLand 是從 Release 下載 AceLib 的。
- [ ] 文件寫明下游的引用方式：在 AceLib 的座標後面加上 `test-fixtures` 後綴。Gradle 的 `testFixtures(...)` 寫法在 JitPack 上解析不到。
- [ ] 可控制的時鐘、排程器、實體退休事件。
- [ ] GUI 與表單的標準假實作，能模擬過時回應、重複回應、關閉失敗。
- [ ] Provider 缺席、停用、重新取得的測試輔助。
- [ ] 一套服務契約測試，真實作和假實作都要通過。

#### 任務完成語意與作用域

現在的排程結果只代表已經排程，動作有沒有做完無從得知。GUI 用自己的結果狀態處理這件事；下游各自拼出「背景計算，再回玩家執行緒」的流程。

要先有 AceLib 1.3.1 的 Folia 任務取消和退休回呼。

- [ ] 排程結果能分辨「已接受排程」和「動作已完成」，可以等待，也可以串接。
- [ ] 任務群組以玩家或實體為作用域。玩家退服、實體退休、plugin 停用時，群組裡的任務自動取消並通知呼叫端。
- [ ] 讀取、背景計算、回到玩家所在執行緒回覆，可以串成一條流程。
- [ ] 驗收情境：玩家退服、跨區移動、排程被拒絕。

#### 事件處理完成後的操作

取消移動事件之後立刻傳送，傳送就算回報成功，位置還是可能被事件處理還原。現有的傳送 API 收到請求就立刻傳送，會遇到同一個問題。ChunkLand 的做法是自己組合下一 tick、玩家執行緒、非同步傳送和失敗回報。

- [ ] 延後傳送：排到之後的 tick，在玩家所在的執行緒傳送，完成時確認玩家真的到了目的地，沒到就回報失敗。
- [ ] 同樣的延後方式可以用在傳送以外的操作。
- [ ] 驗收情境：傳送回報成功卻被還原。
- [ ] Paper 實機驗證。
- [ ] Folia 實機驗證。

### 第二階段 設定與訊息

#### 設定的啟動、快照與型別綁定

ChunkLand 自己寫了設定啟動解析，Ace-Economy 自己寫了設定轉接和嚴格驗證。現有的 `ConfigManager` 有三個缺口：檔案不存在就建立預設檔，分不出首次安裝和用過之後被刪；交給下游的設定物件可以被改動；schema 只檢查必填欄位在不在。

設定損壞時要禁止哪些操作，由下游 plugin 決定。

- [ ] 啟動結果分四類：首次安裝、有效設定、損壞設定、使用後缺檔。
- [ ] 保留最後一次驗證成功的設定副本。
- [ ] 設定損壞時不覆寫操作者的原檔，呼叫端可以指定保守的後備設定。
- [ ] 整份設定先驗證，通過後一次發布不可變的快照。同一輪操作固定用同一個快照。
- [ ] 設定對應到 record 或一般類別。型別、數值範圍、列舉值在載入時驗證，錯誤訊息帶出完整路徑。
- [ ] 監看檔案變更並自動重載。新內容驗證失敗時保留舊快照，記錄原因。
- [ ] 寫回時保留註解，缺的 key 補上預設值和說明。

#### 插件作用域的訊息與在地化

ChunkLand 有自己的訊息管線，Ace-Economy 有設定與語系轉接。現有的 `LangManager` 只讀磁碟上的語系檔，plugin 內建的資源讀不到。

玩家語系偏好存在哪裡不做規定，下游可以用自己的資料庫。

- [ ] 以 plugin 為作用域的工廠，統一建立和清理訊息服務。
- [ ] 玩家語系解析器可以替換。
- [ ] 磁碟上的自訂文案優先，缺的 key 才讀內建資源。
- [ ] 升級時只補新 key，伺服器管理員改過的文案不動。
- [ ] 聊天、ActionBar、GUI、表單共用同一份渲染結果。
- [ ] 顯示標籤和程式識別字分開。
- [ ] 缺 key 和渲染失敗都能診斷。

### 第三階段 介面與指令

#### 介面流程與元件

兩個下游都在現有的 GUI 與表單服務上面，各自維護導航狀態、點擊監聽和表單 session。GUI 服務沒有點擊回呼，下游得自己監聽 inventory 事件。ChunkLand 還拿「受保護欄位被拒絕」的錯誤碼當按鈕訊號。

授權、價格、操作對象仍由下游判斷。佈局引擎和資料綁定不做。

動工前要完成任務完成語意與作用域和 AceLib 1.3.1 的 reload 修正。GUI 服務的作用域依[待決事項](#待決事項)第一項的決定。

流程：

- [ ] 每個 plugin 取得自己的 GUI 作用域 handle，只能操作自己開的 GUI；公開介面上關閉整個服務的方法移除。
- [ ] 玩家開著別的 plugin 的 GUI 時，新的 GUI 取代舊的，並通知原本的 plugin。
- [ ] `open`、`push`、`replace`、`back`、`close` 五個導航操作。
- [ ] 同一份流程對應 Java GUI 和基岩表單兩種呈現。
- [ ] 非同步載入、錯誤畫面、返回狀態。
- [ ] 共用的一次性確認票券。
- [ ] 回應過時、玩家退服、plugin 停用時自動失效。
- [ ] 送出時重新驗證的回呼入口。

元件：

- [ ] 按鈕與點擊回呼、分頁、確認視窗。
- [ ] 輸入提示，支援聊天輸入和鐵砧。
- [ ] 欄位預設全部擋下，只開放指定的欄位。按鈕內建點擊冷卻。

#### 型別化的指令框架

現有的指令模型沒有給下游的正式組裝入口，[指令模型](modules/command.md)頁要下游先用 Paper 自己的指令 API。Ace-Economy 仍然大量引用這個模組，但還沒有提出具體痛點，所以這一項排在介面之後。

宣告方式先做 builder 風格。底層改用 Paper 的 Brigadier 指令註冊方式，現有的 `SubCommandSpec` 留作相容層。

基岩版玩家透過 Geyser 連線時，補全只認得指令結構裡固定的選項，伺服器即時算出來的建議送不到基岩版。這一項要讓基岩版玩家也有堪用的補全。

- [ ] 底層改用 Brigadier 註冊，指令不必再寫進 `plugin.yml`。
- [ ] AceLib 自己的 reload 配合 Brigadier 的註冊時機調整。
- [ ] 給下游的正式組裝入口。
- [ ] 引數型別：玩家、離線玩家、整數與小數範圍、時間長度、世界、列舉、材質。
- [ ] 依引數型別自動補全，依權限過濾說明，錯誤訊息走在地化。
- [ ] 固定的選項以基岩版看得到的方式註冊，讓 Geyser 玩家也有補全。
- [ ] 實測各引數型別在基岩版的補全，結果記在模組頁。
- [ ] 沿用現有的冷卻。
- [ ] Paper 實機驗證：指令在哪個執行緒執行、輸入錯誤的提示、補全。
- [ ] Folia 實機驗證：指令在哪個執行緒執行、輸入錯誤的提示、補全。

### 第四階段 資料與整合

#### 儲存層與玩家資料

目前沒有下游使用玩家資料和資料儲存模組，這一項是維護者決定排入的。玩家資料服務維持在 AceLib 啟動時就啟動；現在的做法是玩家離線時重寫整個檔案。

- [ ] 每位玩家獨立儲存。預設 SQLite，可以換成 MySQL。
- [ ] 資料模型以 record 宣告，編解碼由 AceLib 處理。
- [ ] 登入前預先載入，資料就緒時發出事件。
- [ ] 定期保存。伺服器異常結束時，最多遺失一個保存週期的變更。
- [ ] 可以讀取離線玩家的資料。
- [ ] JDBC store 保存時只寫有變動的資料。

#### 外部整合門面

外部整合模組現在只回報 Vault、LuckPerms、PlaceholderAPI、Floodgate 在不在。ChunkLand 自己維護 Vault 的探測、轉接和不可用時的替代實作；權限、佔位符、區域保護三類目前沒有下游提出需求。

AceLib 只包裝外部 plugin 的服務。

- [ ] 經濟：查餘額、扣款、入帳。
- [ ] 權限：查群組與情境。
- [ ] 佔位符：註冊自己的佔位符。
- [ ] 區域保護：查玩家能不能在某個位置建造。
- [ ] 外部 plugin 不在時，回報明確的不可用結果。

#### 每位玩家的顯示工具

在 Folia 上，每位玩家的顯示更新要回到該玩家所在的執行緒，這一項把排程和清理包起來。目前沒有下游提出需求。

- [ ] 計分板。
- [ ] BossBar。
- [ ] 全息字。

#### 生命週期宿主

AceLib 自己的 reload 已經有提交與回滾的流程，這一項把它抽出來給下游用。

它排在最後。前面各項的服務都要由它接線，那些服務穩定之前做不了。目前也沒有下游提出需求。

- [ ] 下游 plugin 宣告自己的模組和相依關係。
- [ ] 啟用順序、停用順序由 AceLib 安排。
- [ ] reload 和失敗回滾由 AceLib 安排。

### 發布前要確認的事

- [ ] 每一項都有模組文件，consumer 範例能用新 API 編譯。
- [ ] 有下游佐證的項目，ChunkLand 或 Ace-Economy 至少一個實際改用新 API，並刪掉對應的自有實作。
- [ ] 新增的公開型別已分類，簽章基線已更新，既有簽章沒有變動。
- [ ] 牽涉時序和執行緒的項目完成 Paper 與 Folia 實機驗證。

## 候選功能

還沒排入版本的項目：

- 事件優先級，以及忽略已取消事件的選項。目前固定為一般優先級。
- 以註解宣告指令。等 builder 風格的指令框架穩定後再評估。

## 不在範圍內

- 自訂物品的行為註冊。物品模組維持現有的識別、序列化和遷移。
- 自製經濟系統或權限系統。
- 下游 plugin 的領域規則，例如領地授權、價格、交易條件。
- 跨伺服器的資料同步和分散式訊息系統。
- 網頁後台和自動更新。
- 通用的物件關聯對應。
- GUI 的佈局引擎和資料綁定。
- 持久操作紀錄和外部副作用的恢復框架。防止重複扣款是經濟提供者的責任。

## 待決事項

決定之後勾選，並在該項底下加一行「決定：」寫結論。這是唯一可以在項目底下加文字的地方。

1. [x] GUI 服務的作用域。GUI 服務目前由所有 plugin 共用，每位玩家同時只能有一個 session，關閉服務的方法也在公開介面上。介面流程要建立在共用服務上，還是讓每個 plugin 取得自己的作用域實例？建議流程以 plugin 為作用域取得，底層的共用服務留著維持相容。

   決定：每個 plugin 取得自己的作用域 handle，只能操作自己開的 GUI；底層共用同一份 session 登記。公開介面上關閉整個服務的方法在 AceLib 1.4.0 移除。玩家開著別的 plugin 的 GUI 時，新的 GUI 取代舊的，原本的 plugin 會收到被取代的通知。

2. [x] 階段之間要不要發布預覽版。全部一起發布，下游要等到最後才用得到第一階段的成果。文件檢查已經有預覽版的路徑。

   決定：全部項目一起發布，階段之間不發布預覽版。

3. [x] 測試套件的發布方式：多模組結構、artifact 座標、JitPack 設定。

   決定：範圍縮小為假實作和契約測試，故障注入、實機驗證範例、專案範本不做。用 Gradle 的 test fixtures 發布，AceLib 維持單一模組；動工時先確認 JitPack 可行。

4. [x] 新 API 的穩定性標示。新模組第一版就列為 Supported，還是先用較寬鬆的分類發布一個版本？

   決定：新 API 不另外標示穩定性。版本之間可以有破壞性變更，變更要先記在這份路線圖，發布時寫進 CHANGELOG。

5. [x] 現有的傳送 API 為什麼沒被採用。下游的傳送流程沒有用世界模組，要先了解原因，才能決定事件處理完成後的操作長什麼樣子。

   決定：原因已查明。現有的傳送 API 收到請求就立刻傳送，沒有延後。在被取消的移動事件裡呼叫，平台會把玩家放回原位，API 仍回報成功，所以 ChunkLand 自己排到之後的 tick 再傳送。

6. [x] 持久操作紀錄的做法。一種是做成通用框架；另一種是讓 AceLib 的經濟門面在偵測到支援的提供者時傳遞操作識別碼，由提供者端去重。

   決定：不做。防止重複扣款是經濟提供者的責任，持久操作紀錄移到不在範圍內。

7. [x] 玩家資料服務的啟動時機。改成有下游註冊才啟動是行為變更，要先確認有沒有未列入對照的使用者。

   決定：維持現狀，AceLib 啟動時就啟動玩家資料服務。
